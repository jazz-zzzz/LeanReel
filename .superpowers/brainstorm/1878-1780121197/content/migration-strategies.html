核心痛点分析：为什么 PySide6 对 Agent 开发不友好

UI 与业务逻辑的耦合是长期维护的最大阻力

当前 PySide6：紧耦合
❌ 问题 1：Agent 难以产出高质量 Qt 代码
QPropertyAnimation(QObject, b"maximumHeight")
QEasingCurve::OutQuart
→ Agent 缺乏足够的 Qt/C++ 训练数据
❌ 问题 2：UI 逻辑与业务逻辑交织
MainWindow 直接持有 Controller 引用
Panel 内部直接修改 AppState
→ 改 UI 可能破坏业务逻辑
❌ 问题 3：CSS 子集无法表达现代 UI
QSS 不支持 transition / animation
不支持 flexbox / grid 的完整语义
→ 设计意图无法直接翻译为代码
Tauri：天然的关注点分离
✓ 优势 1：Web 前端 = Agent 的母语
transition: opacity 200ms ease-out
@keyframes slideIn { ... }
→ Agent 训练数据中 Web 内容占比极高
✓ 优势 2：前后端天然隔离
Frontend: HTML/CSS/JS (纯 UI)
Backend: Rust Commands (纯业务)
→ 改 UI 零风险触碰业务逻辑
✓ 优势 3：完整的 Web 平台能力
CSS Grid/Flexbox 完整支持
CSS Animations / Transitions 全覆盖
→ 设计稿直接映射为代码

迁移策略选择

从 PySide6 到 Tauri 的路径不是二元选择，有渐进式选项

A

完全重写

弃用 Python，全部用 Rust + Web 前端重写。工程量最大，但架构最干净，彻底解耦。

B

Hybrid：Tauri Shell + Python 后端

Tauri 做窗口壳和 Web 前端，通过 sidecar/子进程调用 Python 业务逻辑。业务逻辑逐步迁移到 Rust。

C

轻量方案：pywebview 替代 PySide6

保持 Python，但用 WebView 渲染 UI。动效问题解决，耦合问题部分改善（需自行架构分离）。

D

原地优化：重构 PySide6 架构 + 动效

不换框架，但重构 UI/业务分离（MVVM），用 QML/Qt Quick 替代 Qt Widgets 改善动效。
